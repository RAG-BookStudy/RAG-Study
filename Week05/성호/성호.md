## Chapter 4. Model - 다양한 LLM 모델 활용

### 왜 여러 모델을 알아야 하는가?

처음에 LangChain 공부할 때 그냥 OpenAI GPT만 쓰면 되는 거 아닌가 싶었다.

근데 실제로 프로젝트를 진행하다 보면:

1. **비용 문제** → GPT-4는 비싸다. 간단한 작업에 GPT-4 쓰면 돈 낭비
2. **속도 문제** → 실시간 응답이 필요한데 모델이 느리면 UX 망함
3. **특화 기능** → 검색 기능이 내장된 Perplexity, 한국어 특화 모델 등

결국 **상황에 맞는 모델을 선택하는 능력**이 중요하다는 걸 깨달았다.

---

### 주요 LLM 모델 비교

직접 공부하면서 정리한 모델별 특징:

| 모델                  | 특징                   | 언제 쓰면 좋을까?          |
| :-------------------- | :--------------------- | :------------------------- |
| **GPT-4.1**           | 가장 강력, 1M 컨텍스트 | 복잡한 추론, 긴 문서 처리  |
| **GPT-4.1-mini**      | 저렴하고 빠름          | 일반적인 대화, 비용 최적화 |
| **Claude 3.5 Sonnet** | 코딩 능력 우수         | 코드 생성, 분석 작업       |
| **Perplexity**        | 실시간 검색 내장       | 최신 정보 필요할 때        |
| **Solar (Upstage)**   | 한국어 특화            | 한국어 프로젝트            |

**실습 코드 - 여러 모델 사용하기:**

```python
from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic

# OpenAI 모델
gpt = ChatOpenAI(
    temperature=0,
    model_name="gpt-4.1-mini",
)

# Anthropic Claude 모델
claude = ChatAnthropic(model_name="claude-3-5-sonnet-20241022")

# 같은 질문을 다른 모델에게
question = "사랑이 뭔가요?"

gpt_answer = gpt.invoke(question)
claude_answer = claude.invoke(question)
```

**느낀 점:** LangChain의 장점이 여기서 드러난다. 모델을 바꿔도 코드 구조가 거의 동일하다. `ChatOpenAI`를 `ChatAnthropic`으로 바꾸기만 하면 끝.

---

### 캐싱(Caching)으로 비용 절감하기

이게 진짜 실용적인 기능이다. 같은 질문을 여러 번 하면 API를 매번 호출할 필요가 없다.

**캐싱이 필요한 이유:**

1. **비용 절감** → 동일 질문에 대한 중복 API 호출 방지
2. **속도 향상** → 캐시된 응답은 즉시 반환

**InMemoryCache 사용법:**

```python
from langchain.globals import set_llm_cache
from langchain.cache import InMemoryCache

# 인메모리 캐시 설정
set_llm_cache(InMemoryCache())

# 첫 번째 호출 - API 실제 호출 (느림)
response1 = chain.invoke({"country": "한국"})

# 두 번째 호출 - 캐시에서 반환 (빠름!)
response2 = chain.invoke({"country": "한국"})
```

**SQLite Cache - 영구 저장:**

```python
from langchain_community.cache import SQLiteCache
from langchain_core.globals import set_llm_cache

# SQLite 캐시 설정 - 파일로 저장되어 프로그램 재시작 후에도 유지
set_llm_cache(SQLiteCache(database_path="cache/llm_cache.db"))
```

| 캐시 종류       | 특징                                 | 적합한 상황 |
| :-------------- | :----------------------------------- | :---------- |
| `InMemoryCache` | 메모리에 저장, 프로그램 종료 시 삭제 | 개발/테스트 |
| `SQLiteCache`   | 파일로 저장, 영구 보관               | 프로덕션    |

### 토큰 사용량 추적

비용 관리를 위해 토큰 사용량을 추적하는 것도 중요하다.

```python
from langchain.callbacks import get_openai_callback
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model_name="gpt-4.1-mini")

# callback으로 토큰 사용량 추적
with get_openai_callback() as cb:
    result = llm.invoke("대한민국의 수도는 어디야?")
    print(f"총 사용된 토큰수: {cb.total_tokens}")
    print(f"프롬프트에 사용된 토큰수: {cb.prompt_tokens}")
    print(f"답변에 사용된 토큰수: {cb.completion_tokens}")
    print(f"호출에 청구된 금액(USD): ${cb.total_cost}")
```

**주의:** 현재 `get_openai_callback()`은 OpenAI API에만 작동한다. 다른 모델은 별도 방법 필요.

## Chapter 5. Memory - 대화 기억하기

### 왜 Memory가 필요한가?

LLM은 기본적으로 **상태가 없다(stateless)**. 이전 대화를 기억하지 못한다.

예를 들어:

```
User: 내 이름은 테디야
AI: 안녕하세요, 테디님!

User: 내 이름이 뭐였지?
AI: 죄송합니다, 저는 당신의 이름을 모릅니다.  ← ???
```

이런 문제를 해결하려면 **대화 기록을 어딘가에 저장**하고, 매번 프롬프트에 함께 넘겨줘야 한다. 이게 Memory의 역할이다.

---

### Memory 종류별 비교

| Memory 종류                       | 저장 방식             | 장점                      | 단점                       |
| :-------------------------------- | :-------------------- | :------------------------ | :------------------------- |
| `ConversationBufferMemory`        | 모든 대화 저장        | 구현 간단, 정보 손실 없음 | 대화 길어지면 토큰 폭발    |
| `ConversationBufferWindowMemory`  | 최근 K개만 저장       | 토큰 수 제한 가능         | 오래된 정보 유실           |
| `ConversationSummaryMemory`       | 대화를 요약해서 저장  | 긴 대화도 압축            | 요약 시 LLM 추가 호출 필요 |
| `ConversationSummaryBufferMemory` | 최근 대화 + 이전 요약 | 두 장점 결합              | 구현 복잡도 증가           |

**내 생각:** 대부분의 경우 `ConversationBufferWindowMemory`로 시작해서, 필요하면 `ConversationSummaryBufferMemory`로 업그레이드하는 게 좋을 것 같다.

---

### ConversationBufferMemory 실습

가장 기본적인 메모리. 모든 대화를 그대로 저장한다.

```python
from langchain.memory import ConversationBufferMemory

memory = ConversationBufferMemory()

# 대화 저장
memory.save_context(
    inputs={"human": "안녕하세요, 계좌를 개설하고 싶습니다."},
    outputs={"ai": "안녕하세요! 신분증을 준비해 주세요."}
)

memory.save_context(
    inputs={"human": "네, 준비했습니다."},
    outputs={"ai": "감사합니다. 신분증을 업로드해 주세요."}
)

# 저장된 대화 확인
print(memory.load_memory_variables({})["history"])
```

**출력:**

```
Human: 안녕하세요, 계좌를 개설하고 싶습니다.
AI: 안녕하세요! 신분증을 준비해 주세요.
Human: 네, 준비했습니다.
AI: 감사합니다. 신분증을 업로드해 주세요.
```

**Chain에 적용하기:**

```python
from langchain_openai import ChatOpenAI
from langchain.chains import ConversationChain

llm = ChatOpenAI(temperature=0, model_name="gpt-4.1-mini")

conversation = ConversationChain(
    llm=llm,
    memory=ConversationBufferMemory(),
)

# 대화 시작
response = conversation.predict(input="안녕하세요, 제 이름은 테디입니다.")
print(response)

# 이전 대화 기억하는지 확인
response = conversation.predict(input="제 이름이 뭐였죠?")
print(response)  # "테디"라고 답변함!
```

### ConversationBufferWindowMemory - 최근 K개만 기억

대화가 길어지면 토큰이 너무 많아진다. 이때 최근 K개의 대화만 유지하는 방법.

```python
from langchain.memory import ConversationBufferWindowMemory

# 최근 2개의 대화만 기억
memory = ConversationBufferWindowMemory(k=2, return_messages=True)

# 6개의 대화를 저장
memory.save_context({"human": "1번 질문"}, {"ai": "1번 답변"})
memory.save_context({"human": "2번 질문"}, {"ai": "2번 답변"})
memory.save_context({"human": "3번 질문"}, {"ai": "3번 답변"})
memory.save_context({"human": "4번 질문"}, {"ai": "4번 답변"})
memory.save_context({"human": "5번 질문"}, {"ai": "5번 답변"})
memory.save_context({"human": "6번 질문"}, {"ai": "6번 답변"})

# 확인 - 최근 2개만 남아있음!
print(memory.load_memory_variables({})["history"])
# 5번, 6번 대화만 출력됨
```

**언제 쓸까?**

- 일반적인 챗봇에서 맥락 유지가 너무 길 필요 없을 때
- 토큰 비용을 절약하고 싶을 때

---

### ConversationSummaryMemory - 요약해서 기억

긴 대화를 **LLM이 요약**해서 저장한다. 토큰은 절약되지만, 요약할 때 LLM을 한 번 더 호출해야 한다.

```python
from langchain.memory import ConversationSummaryMemory
from langchain_openai import ChatOpenAI

memory = ConversationSummaryMemory(
    llm=ChatOpenAI(model_name="gpt-4.1-mini", temperature=0),
    return_messages=True
)

# 여러 대화 저장
memory.save_context(
    inputs={"human": "유럽 여행 패키지의 가격은 얼마인가요?"},
    outputs={"ai": "유럽 14박 15일 패키지의 기본 가격은 3,500유로입니다..."}
)
memory.save_context(
    inputs={"human": "주요 관광지는 어디인가요?"},
    outputs={"ai": "파리의 에펠탑, 로마의 콜로세움...을 방문합니다."}
)
# ... 더 많은 대화 저장

# 확인 - 요약된 내용으로 저장되어 있음!
print(memory.load_memory_variables({})["history"])
```

**장점:** 아무리 대화가 길어져도 요약본이라 토큰 수가 크게 늘지 않음
**단점:** 세부 정보가 요약 과정에서 손실될 수 있음, LLM 추가 호출 비용

### LCEL에 메모리 추가하기

이전 주차에서 배운 LCEL 체인에 메모리를 연결하는 방법이다. 조금 복잡하지만 유연하다.

```python
from operator import itemgetter
from langchain.memory import ConversationBufferMemory
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables import RunnableLambda, RunnablePassthrough
from langchain_openai import ChatOpenAI

# 모델
model = ChatOpenAI(model_name="gpt-4.1-mini")

# 프롬프트 - chat_history 자리 마련
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful chatbot"),
    MessagesPlaceholder(variable_name="chat_history"),  # 여기에 대화 기록 들어감
    ("human", "{input}"),
])

# 메모리
memory = ConversationBufferMemory(return_messages=True, memory_key="chat_history")

# 체인 구성
chain = (
    RunnablePassthrough.assign(
        chat_history=RunnableLambda(memory.load_memory_variables)
        | itemgetter("chat_history")
    )
    | prompt
    | model
)

# 대화 실행
response = chain.invoke({"input": "안녕하세요, 제 이름은 테디입니다."})
print(response.content)

# 메모리에 저장 (수동으로 해야 함!)
memory.save_context(
    {"human": "안녕하세요, 제 이름은 테디입니다."},
    {"ai": response.content}
)

# 다음 대화
response = chain.invoke({"input": "제 이름이 뭐였죠?"})
print(response.content)  # 테디라고 답변!
```

**핵심 포인트:**

1. `MessagesPlaceholder`로 대화 기록이 들어갈 자리를 만든다
2. `RunnablePassthrough.assign`으로 메모리에서 대화 기록을 불러온다
3. **메모리 저장은 수동으로 해야 한다** → `memory.save_context()` 호출 필요

**더 깔끔한 방법 - 커스텀 클래스:**

```python
from langchain_core.runnables import Runnable
from langchain_core.output_parsers import StrOutputParser

class MyConversationChain(Runnable):
    def __init__(self, llm, prompt, memory, input_key="input"):
        self.memory = memory
        self.input_key = input_key
        self.chain = (
            RunnablePassthrough.assign(
                chat_history=RunnableLambda(self.memory.load_memory_variables)
                | itemgetter(memory.memory_key)
            )
            | prompt
            | llm
            | StrOutputParser()
        )

    def invoke(self, query, configs=None, **kwargs):
        answer = self.chain.invoke({self.input_key: query})
        # 자동으로 메모리에 저장!
        self.memory.save_context(
            inputs={"human": query},
            outputs={"ai": answer}
        )
        return answer

# 사용
conversation = MyConversationChain(llm, prompt, memory)
conversation.invoke("안녕하세요!")  # 자동으로 메모리에 저장됨
```

## 헷갈렸던 부분

### return_messages=True vs False

메모리 생성할 때 `return_messages` 옵션이 있는데, 처음엔 뭔 차이인지 몰랐다.

```python
# return_messages=False (기본값)
memory = ConversationBufferMemory()
print(memory.load_memory_variables({})["history"])
# 출력: "Human: 안녕\nAI: 반가워요"  ← 문자열

# return_messages=True
memory = ConversationBufferMemory(return_messages=True)
print(memory.load_memory_variables({})["history"])
# 출력: [HumanMessage(content='안녕'), AIMessage(content='반가워요')]  ← 메시지 객체 리스트
```

**결론:**
| 옵션 | 반환 형태 | 사용 상황 |
|:---|:---|:---|
| `return_messages=False` | 문자열 | `PromptTemplate` 사용 시 |
| `return_messages=True` | 메시지 객체 리스트 | `ChatPromptTemplate` + `MessagesPlaceholder` 사용 시 |

> LCEL에서 `MessagesPlaceholder`를 쓰려면 **반드시 `return_messages=True`**로 해야 한다!

---

### memory_key는 뭐고 왜 맞춰야 하나?

처음에 이 코드 보고 왜 `memory_key`랑 `MessagesPlaceholder`의 `variable_name`이 같아야 하는지 이해가 안 됐다.

```python
# 메모리 생성
memory = ConversationBufferMemory(
    return_messages=True,
    memory_key="chat_history"  # ← 이 이름이
)

# 프롬프트
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful chatbot"),
    MessagesPlaceholder(variable_name="chat_history"),  # ← 여기랑 같아야 함!
    ("human", "{input}"),
])
```

**왜 같아야 하나?**

`memory.load_memory_variables({})`를 호출하면 딕셔너리가 반환된다:

```python
{"chat_history": [HumanMessage(...), AIMessage(...)]}
```

이 딕셔너리의 키(`chat_history`)가 프롬프트의 `variable_name`과 일치해야 값이 제대로 들어간다.

> 쉽게 말해: **memory_key = 프롬프트에서 대화 기록 넣을 변수명**

### ConversationChain vs LCEL 방식

둘 다 메모리를 사용한 대화를 구현하는데, 뭘 써야 할지 헷갈렸다.

**ConversationChain 방식:**

```python
from langchain.chains import ConversationChain

conversation = ConversationChain(
    llm=llm,
    memory=ConversationBufferMemory(),
)
response = conversation.predict(input="안녕")  # 자동으로 메모리 저장됨
```

**LCEL 방식:**

```python
chain = (
    RunnablePassthrough.assign(chat_history=...)
    | prompt
    | model
)
response = chain.invoke({"input": "안녕"})
memory.save_context(...)  # 수동으로 저장해야 함
```

|                     | ConversationChain             | LCEL                  |
| :------------------ | :---------------------------- | :-------------------- |
| **메모리 저장**     | 자동                          | 수동                  |
| **커스터마이징**    | 제한적                        | 자유로움              |
| **deprecated 여부** | LangChain에서 deprecated 예정 | 권장 방식             |
| **적합한 상황**     | 빠른 프로토타입               | 프로덕션, 복잡한 로직 |

**내 결론:** `ConversationChain`이 편하긴 한데, LangChain이 LCEL로 방향을 잡고 있어서 LCEL 방식에 익숙해지는 게 좋을 것 같다.

### 캐시가 안 먹히는 경우

캐시 설정했는데 왜 매번 API 호출되지? 하고 헷갈렸던 경우들:

**1. 입력이 조금이라도 다르면 캐시 미스**

```python
# 이 둘은 다른 캐시 키로 취급됨
chain.invoke({"country": "한국"})
chain.invoke({"country": "한국 "})  # 뒤에 공백 하나 → 캐시 미스!
```

**2. temperature가 0이 아니면 의미 없음**

```python
llm = ChatOpenAI(temperature=0.7)  # 매번 다른 응답 → 캐시해도 의미 없음
```

**3. 스트리밍에서는 캐시 동작이 다름**

```python
# invoke()는 캐시 잘 됨
response = chain.invoke({"query": "질문"})

# stream()은 캐시 구현에 따라 다름 (일부 캐시는 지원 안 함)
for chunk in chain.stream({"query": "질문"}):
    print(chunk)
```

**4. 캐시 스코프 주의**

```python
set_llm_cache(InMemoryCache())  # 전역 설정 → 모든 LLM에 적용됨
# 특정 LLM만 캐시하고 싶으면 다른 방법 필요
```

## 궁금해서 더 찾아본 내용

공부하다가 궁금한 것들이 생겨서 추가로 조사해봤다.

### 1. 멀티 유저 환경에서 메모리 관리는 어떻게?

> "100명이 동시에 챗봇 쓰면 메모리가 섞이지 않나?"

찾아보니 **session_id별로 메모리를 분리**하는 방법이 있었다.

```python
from langchain.memory import ConversationBufferMemory

# 유저별 메모리를 저장할 딕셔너리
user_memories = {}

def get_memory_for_user(session_id: str):
    """session_id별로 별도의 메모리 인스턴스 반환"""
    if session_id not in user_memories:
        user_memories[session_id] = ConversationBufferMemory(
            return_messages=True,
            memory_key="chat_history"
        )
    return user_memories[session_id]

# 사용 예시
user_a_memory = get_memory_for_user("user_123")
user_b_memory = get_memory_for_user("user_456")
# → 각자 독립적인 대화 기록 유지!
```

더 나은 방법으로는 **RunnableWithMessageHistory**를 사용하는 방법도 있다고 한다:

```python
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_community.chat_message_histories import ChatMessageHistory

# 세션별 히스토리 저장소
store = {}

def get_session_history(session_id: str):
    if session_id not in store:
        store[session_id] = ChatMessageHistory()
    return store[session_id]

# 체인에 히스토리 기능 래핑
with_history = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="input",
    history_messages_key="chat_history",
)

# 세션 ID 지정해서 호출
response = with_history.invoke(
    {"input": "안녕"},
    config={"configurable": {"session_id": "user_123"}}
)
```

**결론:** 딕셔너리로 관리하거나 `RunnableWithMessageHistory`를 쓰면 된다.

### 2. 메모리가 계속 커지면 어떻게 되나?

> "ConversationBufferMemory로 대화 계속 쌓으면 터지지 않나?"

세 가지 문제가 발생할 수 있다:

**문제 1: Context Window 초과**

- GPT-4의 경우 128K 토큰 제한
- 대화가 이 한도를 넘으면 API 에러 발생

**문제 2: 비용 폭발**

- 매 요청마다 전체 대화 기록이 프롬프트로 들어감
- 대화 100턴이면 100턴 분량의 토큰 비용이 매번 청구됨

**문제 3: 응답 품질 저하**

- 너무 긴 컨텍스트는 모델이 중요한 정보를 놓칠 수 있음

**해결책:**

| 방법                              | 설명                         | 적합한 상황 |
| :-------------------------------- | :--------------------------- | :---------- |
| `ConversationBufferWindowMemory`  | 최근 K개만 유지              | 단순 대화   |
| `ConversationSummaryBufferMemory` | 오래된 건 요약, 최근 건 유지 | 긴 대화     |
| `ConversationTokenBufferMemory`   | 토큰 수 기준으로 자르기      | 비용 최적화 |

```python
from langchain.memory import ConversationTokenBufferMemory

# 최대 1000 토큰까지만 유지
memory = ConversationTokenBufferMemory(
    llm=llm,
    max_token_limit=1000,  # 이 토큰 수 넘으면 오래된 것부터 삭제
    return_messages=True
)
```

**결론:** 무한정 쌓으면 안 되고, 적절한 Memory 타입을 선택하거나 토큰 제한을 걸어야 한다.

### 3. 프로덕션에서 메모리 저장소는 뭘 쓰나?

> "InMemory는 서버 재시작하면 날아가는데, 실서비스는?"

찾아보니 LangChain에서 여러 외부 저장소를 지원한다:

| 저장소         | 장점                     | 단점                 | 적합한 상황             |
| :------------- | :----------------------- | :------------------- | :---------------------- |
| **Redis**      | 빠름, TTL 지원           | 메모리 기반이라 비용 | 실시간 채팅, 세션 관리  |
| **PostgreSQL** | 영구 저장, SQL 쿼리 가능 | 상대적으로 느림      | 대화 기록 분석 필요 시  |
| **MongoDB**    | 유연한 스키마            | 복잡한 쿼리 어려움   | 다양한 형태의 대화 저장 |
| **SQLite**     | 설정 간단, 파일 기반     | 동시 접속에 약함     | 개발/테스트, 소규모     |

**Redis 예시:**

```python
from langchain_community.chat_message_histories import RedisChatMessageHistory

history = RedisChatMessageHistory(
    session_id="user_123",
    url="redis://localhost:6379"
)

# 메시지 저장
history.add_user_message("안녕하세요")
history.add_ai_message("반갑습니다!")

# 메시지 조회
print(history.messages)
```

**결론:**

- 빠른 응답이 중요하면 → **Redis**
- 데이터 분석/영구 보관이 중요하면 → **PostgreSQL**
- 빠르게 시작하고 싶으면 → **SQLite**

### 4. ConversationSummaryMemory 요약이 이상하게 되면?

> "LLM이 중요한 정보를 요약에서 빼먹으면 어쩌지?"

찾아보니 **요약 프롬프트를 커스터마이징**할 수 있었다:

```python
from langchain.memory import ConversationSummaryMemory
from langchain.prompts import PromptTemplate

# 커스텀 요약 프롬프트
custom_summary_prompt = PromptTemplate(
    input_variables=["summary", "new_lines"],
    template="""현재까지의 대화 요약:
{summary}

새로운 대화:
{new_lines}

위 내용을 바탕으로 요약을 업데이트해주세요.
중요: 사용자 이름, 선호도, 요청사항은 반드시 포함해주세요.
"""
)

memory = ConversationSummaryMemory(
    llm=llm,
    prompt=custom_summary_prompt,  # 커스텀 프롬프트 적용
    return_messages=True
)
```

**요약 품질을 높이는 팁:**

1. **명확한 지시** - 요약에 꼭 포함해야 할 항목 명시
2. **좋은 요약 모델** - 요약용으로 GPT-4 대신 저렴한 mini 모델 써도 됨
3. **하이브리드 방식** - `ConversationSummaryBufferMemory`로 최근 대화는 원본 유지

**결론:** 프롬프트 커스터마이징으로 요약 품질을 제어할 수 있다.

### 5. 캐시 무효화(invalidation)는 어떻게?

> "오늘 날씨를 캐시했는데 내일도 같은 답변 나오면 안 되잖아"

찾아보니 몇 가지 방법이 있었다:

**방법 1: TTL(Time To Live) 지원 캐시 사용**

```python
from langchain_community.cache import RedisCache
from langchain_core.globals import set_llm_cache
import redis

# Redis는 TTL을 기본 지원
redis_client = redis.Redis.from_url("redis://localhost:6379")
set_llm_cache(RedisCache(redis_client, ttl=3600))  # 1시간 후 만료
```

**방법 2: 수동으로 캐시 클리어**

```python
from langchain.globals import set_llm_cache
from langchain.cache import InMemoryCache

cache = InMemoryCache()
set_llm_cache(cache)

# 필요할 때 캐시 전체 삭제
cache.clear()
```

**방법 3: 캐시 키에 날짜 포함**

```python
from datetime import date

# 날짜를 쿼리에 포함시켜서 매일 다른 캐시 키 생성
today = date.today().isoformat()
query = f"[{today}] 오늘 날씨 어때?"

chain.invoke({"query": query})  # 날짜가 바뀌면 자동으로 캐시 미스
```

**방법 4: 동적 정보는 캐시 안 함**

```python
# 정적 정보 (캐시 O)
chain.invoke({"query": "파이썬에서 리스트 정렬하는 방법"})

# 동적 정보 (캐시 X) - 아예 캐시를 안 쓰거나 별도 처리
realtime_chain.invoke({"query": "오늘 날씨"})
```

**결론:**

- TTL 지원 캐시(Redis) 사용하거나
- 동적 정보는 캐시 대상에서 제외하거나
- 캐시 키에 시간 정보를 포함시킨다

## 이번 주 핵심 정리

1. **모델은 상황에 맞게 선택** → GPT-4는 비싸니까, 간단한 건 mini 모델로
2. **캐싱으로 비용 절감** → 같은 질문 반복되면 캐시 활용
3. **토큰 사용량 추적** → `get_openai_callback()`으로 비용 관리
4. **Memory는 필수** → LLM은 기본적으로 상태가 없어서, 대화 기록을 직접 관리해야 함
5. **Memory 종류별 트레이드오프** → 전체 저장 vs 최근 K개 vs 요약
